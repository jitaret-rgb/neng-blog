เดือนกันยายนถึงตุลาคม 2026 มี decision model ออกมาให้เลือกใช้สามตัวในเวลาไม่ถึงเจ็ดสัปดาห์ บทความนี้จะเล่าให้ฟังว่า Clef ตัวจาก Cloudflare เหมาะกับงานอะไร ราคาเท่าไหร่ และผมใช้มันแทน decision engine เดิมใน pipeline ข่าวของตัวเองได้อย่างไร

## บทนำ: System One คืออะไร ทำไมถึงเกิด

ชื่อ System One มาจากแนวคิดเรื่อง System 1 และ System 2 ของ Daniel Kahneman ที่อธิบายไว้ในหนังสือ Thinking, Fast and Slow System 1 คือระบบคิดเร็วที่ตัดสินใจจากสัญชาตญาณและรูปแบบที่จำได้ ใช้ข้อมูลไม่เยอะ ตัดรอบได้ทันที ส่วน System 2 คือระบบคิดช้าที่ไตร่ตรองยาว สายงาน software หยิบแนวคิดแรกมาตั้งเป็นชื่อตระกูล API สำหรับโมเดลที่ทำหน้าที่ตัดสินใจอย่างเดียว

จุดที่ต่างจาก LLM อยู่ที่รูปแบบการตอบ LLM เป็นโมเดลแบบ generative รับข้อความแล้วสร้างข้อความตอบกลับ คำตอบจึงเป็นภาษาอิสระที่ต้องมา parse ทีหลัง บางทีก็ตอบนอกเหนือจากที่เราต้องการ หรือตีความหมายผิดไปจากแบบฟอร์ม

Decision model กลับกันทั้งหมด ฝั่งโค้ดจะส่ง state หรือข้อมูลที่ต้องตัดสินใจ พร้อมกับคำถามที่ระบุชนิดไว้ชัด เช่น เลือกจากตัวเลือกที่กำหนด ให้คะแนนตามเกณฑ์ หรืออ่านค่าจากข้อมูล โมเดลคืนกลับมาเป็น probability ต่อตัวเลือกในรอบเดียว ไม่มีการสร้างข้อความออกมาแม้แต่คำเดียว งานจึงกลายเป็นเรื่องของการอ่านตัวเลขแล้วตัดเกณฑ์ต่อในโค้ด

ในระบบที่ต้องตัดสินใจหลายรอบต่อวัน คำตอบที่มีโครงสร้างคงที่เป็นข้อได้เปรียบ เพราะโค้ดฝั่งรับผลไม่ต้องคอย parse ภาษาหรือกันเคสที่โมเดลตอบนอกแบบ ทุกครั้งที่เรียกได้รูปแบบเดียวกัน และ probability ที่ได้ยังเปิดทางให้ตั้งเกณฑ์ความมั่นใจแยกชั้นได้ เช่น ค่าสูงผ่านอัตโนมัติ ค่ากลางส่งให้คนตรวจต่อ ซึ่งเป็นเรื่องยากถ้าคำตอบเป็นข้อความอิสระจาก LLM

อีกเหตุผลหนึ่งคือเรื่อง latency และต้นทุน งานตัดสินใจส่วนใหญ่ใน pipeline ไม่ได้ต้องการคำตอบยาว ต้องการแค่ว่าอยู่ในหมวดไหนและควรไปต่อทางใด การเรียกโมเดลเล็กที่คืนเฉพาะตัวเลขจึงจบได้เร็วกว่า ทั้งยังประหยัดกว่าการเรียก LLM ขนาดใหญ่มาสร้างข้อความเพื่อให้เราแปลผลใหม่อีกรอบ

สาเหตุที่สาย System One บูมช่วงนี้เพราะทุกคนเจอปัญหาเดียวกัน คือการให้ LLM เดาว่าข้อความนี้ควรไปทีมไหน ควรจัดลำดับความสำคัญแค่ไหน แล้วต้องมาเกรงว่าคำตอบจะเพี้ยน Jev จาก TypeSafe เปิดตัว 15 ก.ย.2026 ตามด้วย Decisions API จาก OpenAI วันที่ 29 ก.ย.2026 และปิดท้ายเดือนด้วย Clef ของ Cloudflare วันที่ 1 ต.ค.2026

## รู้จัก Clef

Cloudflare เปิดตัว Clef วันที่ 1 ต.ค.2026 โดยแบ่งเป็นสามรุ่น คือ `clef` ตัวหลักขนาด 27B สำหรับงานที่ต้องการความแม่นสูง `clef-flash` ขนาด 9B สำหรับงานที่เน้นความเร็ว และ `clef-omni` ที่รองรับงานหลายรูปแบบ ทั้งสามรุ่นเปิดน้ำหนักโมเดล (open weights) ภายใต้ลิขสิทธิ์ Apache 2.0 ดาวน์โหลดได้จาก Hugging Face ใน organization Cloudflare/clef ใครที่อยากนำ weights ไปรันบนเครื่องตัวเองก็ทำได้ ไม่ผูกกับ API ของ Cloudflare เพียงอย่างเดียว

หลักการทำงานของ Clef รับของสองอย่างในการเรียกแต่ละครั้ง อย่างแรกคือ state หรือข้อมูลที่จะใช้ตัดสินใจ ซึ่งส่งมาเป็นข้อความ JSON รูปภาพ หรือสถานะของแอปได้ อย่างที่สองคือ questions ที่กำหนดชนิดคำตอบไว้ เช่น `choice` สำหรับเลือกจากตัวเลือก `noul` สำหรับคำถามใช่หรือไม่ และ `score` สำหรับให้คะแนนตามเกณฑ์ที่เรียงระดับไว้ ผลที่ได้กลับมาคือ probability ของทุกตัวเลือกในรอบเดียว

เนื่องจากโมเดลไม่ได้สร้างข้อความใด ๆ ตอบกลับ คำตอบที่อยู่นอกตัวเลือกที่เรากำหนดจึงเป็นไปไม่ได้เลย ข้อนี้ต่างจาก LLM ที่บางทีตอบนอกแบบฟอร์มโดยไม่มีใครสั่ง

อีกเรื่องที่ทำให้ตัดสินใจย้ายได้เร็ว คือ Clef ใช้ API แบบเดียวกับ System One ของ TypeSafe โค้ดที่เขียนไว้สำหรับ Jev จึงสลับมาเรียก Clef ได้ด้วยการเปลี่ยนชื่อโมเดลเท่านั้น ไม่ต้องเขียน logic ใหม่

Cloudflare วางทั้งสองรุ่นไว้บน Workers AI ใต้ model ID ว่า `@cf/cloudflare/clef` และ `@cf/cloudflare/clef-flash` เรียกผ่าน AI binding ของ Worker ได้ทันที ส่วนความเร็วนั้น changelog วันที่ 1 ต.ค.2026 รายงานค่า median latency ไว้ที่ 209.3 มิลลิวินาทีสำหรับ `clef` และ 38.8 มิลลิวินาทีสำหรับ `clef-flash` เทียบกับ Jev ที่ 524.1 มิลลิวินาที จากการทดสอบ 43 รอบ benchmark

จุดที่ได้เปรียบ Jev ตามสเปกคือมี vision encoder รับรูปภาพได้สูงสุด 4 รูปต่อคำขอ context ยาว 64K เทียบกับ Jev ที่ 32K มีนโยบาย zero data retention และเปิด weights ให้ self-host ได้เต็มรูปแบบ

เรื่องรูปภาพมีรายละเอียดที่ควรรู้ก่อนส่ง Clef รับไฟล์ประเภท PNG JPEG และ WebP สูงสุดสี่รูปต่อคำขอ จำกัดที่สี่ MiB และสิบหกล้านพิกเซลต่อรูป รวมกันไม่เกินแปด MiB เมื่อแปลงเป็น pixel ส่วน body ของคำขอทั้งหมดต้องไม่เกินสิบสาม MiB และต้องส่งเป็นไฟล์แนบเท่านั้น ไม่รับลิงก์ภายนอก

## ใช้อะไรได้บ้าง

งานของ Clef เป็นงานแบบมีตัวเลือกชัดเจน หยิบมาใช้แทน LLM ได้ตรง ๆ ดังนี้

- **Routing ตั๋วและใบแจ้งหนี้** ให้โมเดลตัดสินใจว่าตั๋วเข้ามานี้เร่งด่วนหรือไม่ และทีมไหนควรรับผิดชอบ เพื่อส่งต่ออัตโนมัติโดยไม่ต้องให้คนนั่งดูทุกใบ
- **Intent classification** อ่านข้อความหรือสถานะของผู้ใช้แล้วจัดว่าอยู่ในหมวดไหน ก่อนส่งต่อไปยัง flow ที่ถูกต้อง
- **เลือก tool** ในระบบ agent ว่าคำสั่งชุดนี้ควรเรียก function ตัวไหน probability ที่ได้กลับมาใช้ตัดเกณฑ์ความมั่นใจในโค้ดต่อได้ทันที
- **Guardrail** ตรวจว่าเนื้อหาหรือพฤติกรรมบางอย่างเข้าเกณฑ์ต้องบล็อกหรือไม่
- **ให้คะแนนตาม rubric** แทนการใช้ LLM judge ที่ต้องอ่านคำตอบแล้วเขียนคะแนนกลับมา การให้คะแนนแบบ typed นี้คงที่กว่าและเทียบผลข้ามรอบได้

Cloudflare วางบทบาทของ Clef ไว้คู่กับ LLM ตามที่บล็อกเปิดตัวแนะนำ คือให้ใส่ Clef ไว้ในเส้นทางรับคำขอของ agent ก่อน เพื่อตัดสินใจขั้นแรกว่าควรดำเนินการต่ออย่างไร แล้วส่งงานที่ต้องสร้างคำตอบหรือลงมือทำจริงต่อให้ LLM บน Workers AI เป็นผู้รับช่วง การแบ่งงานแบบนี้ทำให้แต่ละตัวได้ทำในสิ่งที่ตัวเองถนัด คือ decision model รับงานตัดสินใจที่ต้องการความเร็วและต้นทุนต่ำ ส่วน LLM รับงานสร้างภาษาที่ต้องการความยืดหยุ่น

ตัวอย่างจริงจาก Cloudflare คือทีม Threat Intelligence เอา Clef คู่กับ Browser Run ให้ไปเปิดและจำแนกหมวดของโดเมนเว็บ โดยทำได้เสร็จใน 2.2 วินาที ขณะที่ LLM ทั่วไปที่เร็วที่สุดอย่าง gpt-oss-120b ใช้ 4.7 วินาทีใน workflow เดียวกัน และได้ผลลัพธ์แค่สองคลาส

ผลที่ได้เป็น probability ของแต่ละหมวดตามที่บล็อก Cloudflare เคยยกตัวอย่าง เช่น โอกาสที่โดเมนเป็นเว็บแฟชั่น 95% e-commerce 85% และมีโอกาสเป็น phishing ต่ำกว่า 1% ค่าแบบนี้นำไปเทียบเกณฑ์ในระบบได้ทันทีโดยไม่ต้องรอคนมานั่งอ่านผล

ด้าน benchmark ตัวเลขที่ Cloudflare ประกาศคือ BANKING77 macro-F1 ที่ 94.2 สำหรับ Clef และ BFCL แบบ case-exact อยู่ในช่วง 98.5 ถึง 98.8 เมื่อดูภาพรวมบน decision benchmark สิบชุด Cloudflare ระบุว่ามีโมเดลตระกูล Clef ทำคะแนนสูงสุดถึงเจ็ดชุด นำหน้า Jev และโมเดล open อื่นในสายเดียวกัน

อีกเรื่องที่ประกาศพร้อมกันคือบริการปรับแต่งโมเดลด้วย reinforcement learning สำหรับลูกค้าที่ต้องการฝึก Clef ให้เข้ากับงานเฉพาะของตัวเอง ซึ่งตอนนี้เปิดรับสมัครในรูปแบบ design partner ใครที่มีชุดคำตอบย้อนหลังของงานตัวเองอยู่แล้ว จึงมีทางเลือกที่จะยกระดับความแม่นขึ้นไปอีกขั้นในอนาคต

วิธีนำผลไปใช้จะเหมือนกันเกือบทุกงาน คืออ่าน probability ของแต่ละตัวเลือกแล้วเทียบเกณฑ์ที่เขียนไว้ในโค้ด ตัวเลือกไหนได้ค่าสูงก็เดินหน้าต่ออัตโนมัติ ค่าที่ยังกึ่งกลางก็โยนให้คนตัดสินใจแทน สำหรับการให้คะแนนตาม rubric การแทนที่ LLM judge ด้วยโมเดลที่คืนตัวเลขโดยตรงทำให้ผลลัพธ์คงรูปแบบเดิมทุกครั้ง เทียบผลระหว่างรอบหรือย้อนดูว่าคะแนนถดถอยหรือไม่ได้โดยไม่ต้องตีความคำตอบภาษาใหม่ทุกรอบ

### ตัวอย่างแบบก่อนและหลัง

**กรณีที่ 1: จำแนกหมวดเว็บไซต์**: ก่อนใช้ Clef ทีม Threat Intelligence ของ Cloudflare ใช้ LLM ทั่วไปอย่าง gpt-oss-120b ใน workflow เดียวกัน ใช้เวลา 4.7 วินาทีและได้ผลลัพธ์เพียงสองคลาส หลังเปลี่ยนมาใช้ Clef คู่กับ Browser Run เวลาลดเหลือ 2.2 วินาที พร้อมกับ probability ของทุกคลาส เช่น แฟชั่น 95% e-commerce 85% และ phishing ต่ำกว่า 1% ประโยชน์ที่ได้คือความเร็วที่เพิ่มขึ้นเท่าตัว และผลลัพธ์ที่เป็นตัวเลขพร้อมเทียบเกณฑ์ในโค้ดได้ทันที

**กรณีที่ 2: pipeline triage ข่าวของผม**: ช่วงที่ decision engine เดิมค้าง HTTP 500 ผมทำได้เพียงรอและเดาว่าแต่ละ stage ยังทำงานอยู่ไหม พอสลับมาใช้ Clef ตัวเลขทุก stage กลับมาทันที เช่น relevance ผ่าน 14 จาก 17 รายการ และ gate คืนค่า 0.02 กับ 0.74 ทุกเช้ามี cron อ่านค่าเหล่านี้ยืนยันว่าระบบยังตอบจริง ประโยชน์คือการมองเห็นการทำงานของ pipeline ที่หายไปคืนกลับมา และการตัดสินใจว่าจะแก้หรือไม่แก้ทำได้ด้วยตัวเลข

**กรณีที่ 3: ต้นทุนต่อการตัดสินใจ 1 ล้านครั้ง**: ถ้างานรับตั๋วครั้งละ 500 tokens เรียก `clef-flash` 1 ล้านครั้งตกที่ 19 ดอลลาร์ ส่วน median latency ที่ 38.8 มิลลิวินาทีทำให้ตัวตัดสินใจตัวนี้วางบนเส้นทางรับคำขอได้โดยไม่ทำให้ผู้ใช้รู้สึกว่าช้า ประโยชน์คืองบที่คาดการณ์ได้ล่วงหน้ากับเวลาตอบสนองที่พอใส่ใน hot path ได้จริง

## ประโยชน์จากประสบการณ์ใช้จริง

ก่อนรู้จัก Clef ผมใช้ iApp OpenThai SystemOne เป็น decision engine ให้กับ pipeline triage ข่าวของเว็บตัวเอง ซึ่งมีสองรอบต่อวันคือ morning-brief และ evening-brief แต่ละรอบมี decision stage หลายตัวคอยทำงานร่วมกัน ได้แก่ relevance ว่าข่าวนี้เกี่ยวข้องกับโจทย์ไหม rank ว่าควรจัดลำดับความสำคัญแค่ไหน sentiment ว่าเป็นบวกหรือลบ และ gate สุดท้ายที่ตัดสินใจว่าผ่านเกณฑ์จะนำไปเผยแพร่หรือไม่ ช่วง preview ระบบเดิมให้ใช้ฟรี 1,000 decisions ต่อวันต่อ key ซึ่งพอต่อกับงานสองรอบได้พอดี

วันที่ 13 พ.ย.2026 ปัญหาเริ่มขึ้นจริง ๆ เมื่อ API ของ iApp เริ่มค้างและตอบ HTTP 500 ต่อเนื่อง ทั้งที่ไม่มีประกาศปิดบริการที่ไหน และ GitHub issue ที่เปิดไว้ก็ไม่มีใครตอบกลับ ระบบที่เคยให้ตัวเลขกลายเป็นอ่านไม่ได้

ผมลองแก้ด้วยการ self-host บนเครื่องตัวเองก่อน แต่ไม่สำเร็จ เพราะ CPU ที่ใช้เป็น Intel Xeon รุ่น Ivy Bridge ซึ่งไม่มีชุดคำสั่ง AVX2 ทำให้ torch เวอร์ชันใหม่กว่า 2.4 crash ด้วยข้อผิดพลาด invalid opcode ทุกครั้งตอนเริ่มโหลดโมเดล

วันที่ 18 พ.ย.2026 จึงสลับไปใช้ Cloudflare Clef บน Workers AI แทน โดยเปลี่ยนทั้งสอง profile ของ pipeline ผลคือ stage ทุกตัวกลับมาให้ตัวเลขจริงอีกครั้ง relevance ผ่าน 14 จาก 17 รายการ gate ด้านอารมณ์ได้ 0.02 และ gate ด้าน 5W1H ได้ 0.74 ทุกค่าเป็น probability ที่โมเดลคืนมาจริง ไม่มี stage ไหนทำงานแบบ fail-open ให้ผ่านเลยแบบลอย ๆ และมี cron เช็คผลอีกครั้งในวันที่ 19 พ.ย.เวลา 07:30 ยืนยันว่าทุกอย่างทำงานปกติ

ทุกค่าที่ได้อ่านและเทียบกับวันก่อนได้ทันที ในช่วงที่ระบบเดิมเริ่มค้าง ผมทำได้เพียงรอและเดาว่า pipeline ยังทำงานอยู่หรือไม่ การได้ตัวเลขคืนมาจึงเท่ากับการได้การมองเห็นการทำงานของ pipeline กลับมาด้วย

นอกจาก triage ข่าว ผมยังมี publish_gate.py กับ clef_vision.py ที่ใช้ Clef ตรวจรูปก่อนเผยแพร่ เช่น ตรวจว่ามี alt text และรูปตรงกับหัวข้อหรือไม่ ถ้าตรวจไม่ได้ระบบจะ fail-open ตามเดิม เพื่อไม่ให้บทความต้องค้างรอ
ตอนนี้ token ของ Workers AI ถูกเก็บลง backup ไว้แล้ว ทั้งไฟล์ cf-workers-ai.token และ cf-account-id เผื่อต้องย้ายเครื่องหรือกู้ระบบในอนาคต

### บทเรียนที่ได้จากการสลับครั้งนี้

สิ่งแรกคือระบบที่พึ่ง decision engine ภายนอกต้องมีตัวเฝ้าดูจริง ๆ การตั้ง cron ให้ตรวจผลทุกเช้าเป็นสิ่งที่ทำให้ผมรู้วันต่อวันว่าแต่ละ stage ยังคืน probability จริงอยู่ และรู้ทันทีเมื่อค่าหายไปเป็นสถานะ fail-open

สิ่งที่สองคือควรระบุ fail mode ของแต่ละจุดไว้ล่วงหน้า จุดที่มีทางเลือกสองแบบอย่างการตรวจรูปผมเลือกให้ fail-open เพื่อไม่ให้บทความค้าง ส่วน decision stage หลักของ triage ต้องได้ค่าจริงเสมอ ถ้าได้ไม่จริงต้องถือว่าระบบขัดข้องและแจ้งเตือน สิ่งเหล่านี้ต้องเขียนไว้ก่อนเกิดเหตุ ตอนที่ API เจ้าอื่นเริ่มค้างจะได้ไม่ต้องมานั่งตัดสินใจกันใหม่

สิ่งที่สามคือการแยกชั้นระหว่างตัวตัดสินใจกับตัวเฝ้าดู ตัวเฝ้าดูเองก็ไม่ควรมีจุดพึ่งพาจุดเดียว ผมออกแบบให้แต่ละ stage ทำงานต่อได้แบบ fail-open เมื่อเรียกโมเดลไม่ได้ เพื่อให้ข่าวยังส่งถึงมือทันเวลา พร้อมกับบันทึกลง log ทุกรอบว่ารันสำเร็จหรือถูกข้ามด้วยเหตุผลอะไร เมื่อมี log แบบนี้อยู่ การตรวจว่า pipeline ยังทำงานจริงในแต่ละวันจึงเป็นเรื่องของการอ่านตัวเลข ไม่ต้องตั้งคำถามกับความเงียบของระบบ

## ค่าใช้จ่าย

ราคาทั้งหมดอ้างอิงจากหน้าเอกสารของ Cloudflare บน developers.cloudflare.com และ changelog ลงวันที่ 9 ต.ค.2026 ซึ่งเป็นวันที่ปรับราคาครั้งล่าสุดที่ประกาศไว้

| โมเดล | ขนาด | Context (hosted) | ราคา input ต่อ 1M tokens |
| --- | --- | --- | --- |
| `clef` | 27B | 65,536 | $0.24 |
| `clef-flash` | 9B | 24,576 | $0.038 |
| `clef-omni` | ไม่ระบุ | 64K | $0.15 |

ข้อสำคัญคือทุกรุ่นไม่คิดค่า output tokens เพราะโมเดลไม่ได้สร้างข้อความตอบกลับอยู่แล้ว ค่าใช้จ่ายจึงมาจาก input ล้วน ๆ ส่วนรูปภาพคิดเป็น input tokens ตามสูตร (width หาร 32) คูณ (height หาร 32) ตัวอย่างเช่นรูปขนาด 1024 คูณ 1024 pixels จะถูกคิดเป็น 32 คูณ 32 เท่ากับ 1,024 input tokens ต่อรูป ถ้าส่งครบ 4 รูปตามโควตาสูงสุดก็เป็น 4,096 tokens ที่ต้องรวมเข้าไปในค่าใช้จ่ายของคำขอนั้น

ลองคำนวณดูง่าย ๆ สมมติว่าแต่ละคำขอส่งข้อมูลเข้าไป 500 tokens และเรียกใช้ 1 ล้านครั้ง เท่ากับว่าใช้ input ไปทั้งสิ้น 500 ล้าน tokens หรือ 500 หน่วยของราคาต่อ 1M ถ้าใช้ `clef` จะเสีย 500 คูณ $0.24 เท่ากับ $120 ส่วนถ้าใช้ `clef-flash` จะเสีย 500 คูณ $0.038 เท่ากับ $19 เมื่อเฉลี่ยกลับเป็นต่อคำขอเดียวเหลือเพียง 0.012 เซนต์สำหรับ `clef` และ 0.002 เซนต์สำหรับ `clef-flash` งาน triage ข่าวแบบที่ผมทำซึ่งส่งข้อความไม่กี่ร้อย tokens ต่อรายการ จึงมีต้นทุนต่อคำขออยู่ในระดับที่มองข้ามได้

อีกมุมที่ใช้วัดงบได้ชัดคือการดูรายเดือน สมมติ pipeline รับงาน 10 ล้านคำขอต่อเดือน คำขอละ 500 tokens เท่ากับ input 5 พันล้าน tokens หรือ 5,000 หน่วยของราคาต่อ 1M ถ้าใช้ `clef` จะเสีย $1,200 ต่อเดือน ส่วน `clef-flash` เสีย $190 ตัวเลขระดับนี้ทำให้ผู้ดูแลระบบประมาณการงบล่วงหน้าได้ง่าย เพราะค่าใช้จ่ายผูกกับจำนวน token ล้วน ไม่มีส่วนของ output ที่ยาวไม่แน่นอนแบบ LLM ทั่วไป ยิ่งไปกว่านั้นต้นทุนยังแปรผันตรงกับจำนวนคำขอ เมื่อปริมาณงานลดลงค่าใช้จ่ายก็ลดลงตาม ไม่มีค่าใช้จ่ายคงที่รายเดือนที่ต้องแบกรับ

ย้อนไปวันที่ 9 ต.ค.2026 Cloudflare ลดราคา `clef-flash` จาก $0.09 เหลือ $0.038 ซึ่งถูกกว่า Jev ไปพร้อมกับลด hosted context จาก 64K เหลือ 24K เพราะพบว่ามีคำขอแค่ 0.24% ที่ยาวเกิน 24K ส่วน weights บน Hugging Face ยังรองรับ context 256K สำหรับคนที่ self-host

เทียบกับทางเลือกเดิม iApp OpenThai SystemOne ที่ผมเคยใช้เป็นช่วง preview ให้ฟรี 1,000 decisions ต่อวันต่อ key และยังไม่มีราคาทางการออกมา ส่วน LLM ทั่วไปคิดค่าทั้ง input และ output และแต่ละรอบยังตอบเป็นข้อความที่ต้องนำมา parse อีกชั้น ราคาอาจเปลี่ยนได้อีกเมื่อไหร่ก็ได้ จึงควรอ้างอิง changelog เป็นวันที่กำกับไว้เสมอ

## ข้อจำกัดและสิ่งที่ควรรู้ก่อนใช้

Clef ไม่ได้ถูกออกแบบมาแทน LLM ทุกกรณี ข้อจำกัดแรกคือโมเดลตอบได้เฉพาะตัวเลือกที่เรากำหนดไว้เท่านั้น งานที่ต้องสร้างข้อความยาว ร่างคำตอบ หรือให้เหตุผลอิสระ จึงยังต้องใช้ LLM เป็นตัวแยกส่วนกันไป

ข้อสองคือคุณภาพคำตอบผูกกับการออกแบบตัวเลือกโดยตรง ถ้ารายการ choice ไม่ครอบคลุมสถานการณ์จริง probability ที่ได้ก็สะท้อนชุดตัวเลือกแคบ ๆ นั้น นอกจากนี้ state ที่ส่งเข้าไปยาวเกิน context จะถูกตัดให้พอดีโดยอัตโนมัติ จึงต้องระวังอย่าให้ข้อมูลสำคัญหลุดออกไปอยู่ท้าย ๆ ของ payload

ข้อสามเรื่อง hosted context ของ `clef-flash` ที่เหลือ 24,576 tokens หลังการปรับของวันที่ 9 ต.ค.2026 งานที่ยาวกว่านั้นต้องใช้ `clef` ตัวหลัก หรือรับกับการ self-host เพื่อได้ context 256K จาก weights บน Hugging Face

ข้อสี่คือเงื่อนไขฮาร์ดแวร์ตอน self-host ประสบการณ์ตรงของผมคือ CPU Intel Xeon รุ่น Ivy Bridge ไม่มีชุดคำสั่ง AVX2 ทำให้ torch เวอร์ชันใหม่กว่า 2.4 crash ด้วย invalid opcode ทุกครั้ง ก่อนวางแผนรันเองจึงต้องเช็ค instruction set ของเครื่องก่อนว่ารองรับไหม

ข้อห้าคือการพึ่งพาบริการภายนอก ราคาและข้อกำหนดของ Cloudflare ปรับได้เสมอ และเหตุการณ์ที่ API เจ้าอื่นค้าง HTTP 500 หลายวันโดยไม่มีประกาศก็เป็นบทเรียนว่า pipeline ควรมีการออกแบบ fail-over ไว้ล่วงหน้า อย่าง publish gate ของผมที่ตั้งให้ fail-open เมื่อตรวจรูปไม่ได้ และเก็บ token Workers AI ลง backup ไว้เสมอ ส่วนเรื่องข้อมูลแม้ Cloudflare จะมีนโยบาย zero data retention แต่การนำไปใช้ในองค์กรก็ควรเช็คนโยบายให้ตรงกับข้อกำหนดของตัวเองด้วย

อีกข้อหนึ่งที่เจอจากเอกสารคือต่อหนึ่งคำขอถามได้สูงสุด 64 คำถาม งานที่มีหัวข้อตัดสินใจเกินกว่านั้นต้องแบ่งส่งหลายครั้ง ซึ่งกระทบทั้งความเร็วและวิธีเขียนโค้ดฝั่งเรียกใช้ ควรวางโครงสร้างคำถามให้พอดีตั้งแต่แรก

ข้อสุดท้ายเป็นเรื่องของวิธีเริ่มใช้งานมากกว่าตัวโมเดล จากประสบการณ์ย้ายระบบครั้งนี้ผมแนะนำให้รันระบบใหม่คู่กับระบบเดิมไปก่อนในช่วงแรก เก็บผลของทั้งสองฝั่งมาเทียบกันทุกวันว่า probability ที่ Clef คืนมาสอดคล้องกับคำตอบที่คนหรือ LLM เคยให้ไหม เมื่อเห็นว่าค่าสอดคล้องต่อเนื่องหลายวันจึงค่อยปิดระบบเดิม วิธีนี้ใช้เวลาเพิ่มเล็กน้อย แต่ทำให้การย้ายเป็นการตัดสินใจด้วยตัวเลขมากกว่าการคาดเดา

## สรุป: คุ้มไหม ควรใช้ตอนไหน

ถ้าสรุปเป็นบรรทัดเดียว Clef คุ้มสำหรับงานตัดสินใจที่มีตัวเลือกชัดเจนและเรียกใช้ถี่ เพราะได้ทั้งความเร็ว ต้นทุนที่คาดการณ์ได้ และรูปแบบผลลัพธ์ที่คงที่ ส่วนงานที่ต้องการคำตอบแบบภาษาอิสระ ให้หยิบ LLM ไปใช้ตามเดิม

แนวทางที่ผมใช้เองคือเริ่มจาก `clef-flash` ก่อนในทุกจุดที่ต้องการความเร็วและอยากกดต้นทุนให้ต่ำ แล้วสลับขึ้นมาเป็น `clef` เมื่องานนั้นต้องการความแม่นสูงขึ้นหรือมีรูปภาพเข้ามาเกี่ยวข้อง ส่วนใครที่ต้องการคุมทุกอย่างเองทั้งเรื่องข้อมูลและฮาร์ดแวร์ weights ภายใต้ Apache 2.0 บน Hugging Face ก็เปิดทางให้ self-host ได้เต็มที่

การย้ายออกจาก iApp OpenThai SystemOne ของผมมีสาเหตุจากระบบเดิมที่ตอบ HTTP 500 โดยไม่มีกำหนด ผนวกกับเครื่องของตัวเองที่รัน weights เก่าไม่ได้ เมื่อเปลี่ยนมาใช้ Clef บน Workers AI ทั้งสอง profile ผลคือทุก stage ใน pipeline ข่าวกลับมาให้ probability จริงอีกครั้ง ตั้งแต่ relevance ยัน gate สุดท้าย

ใครที่ลังเลว่าจะเริ่มดีไหม ให้ดูที่ธรรมชาติของงานก่อน ถ้าคำตอบคือใช่หรือไม่ เลือกอันไหน ให้กี่คะแนนตามเกณฑ์ Clef เหมาะอยู่แล้ว ถ้าคำตอบต้องเป็นย่อหน้า ให้จับ LLM ราคา ณ 9 ต.ค.2026 ที่ยกมาอ้างในบทความนี้อาจเปลี่ยนไปเมื่อมี changelog ใหม่ จึงควรเช็คหน้าเอกสารก่อนตัดสินใจทำสัญญาหรือประมาณการงบ

ส่วนใครที่ยังไม่ควรใช้ คืองานที่ยังนิยามคำตอบที่ถูกต้องไม่ได้เลย เพราะสิ่งที่ต้องทำก่อนคือการออกแบบคำถามและชุดตัวเลือกให้ครบ เมื่อตอบได้ว่าเกณฑ์ถูกคืออะไร decision model ถึงจะตอบกลับมาได้คุ้มค่า ถ้ายังนิยามไม่ได้ ลองเริ่มจาก LLM เพื่อช่วยร่าง taxonomy ของคำตอบก่อน แล้วค่อยย้ายมาเป็น decision model เมื่อเกณฑ์นิ่งพอ

สำหรับคนที่ดูแลระบบซึ่งต้องตัดสินใจอยู่เป็นประจำ การเริ่มทดลองด้วย `clef-flash` ทีละจุดก่อนเป็นวิธีที่เห็นผลเร็ว เพราะตั้งค่าน้อยและค่าใช้จ่ายระหว่างทดลองอยู่ในระดับที่ไม่กระทบงบ เมื่อมั่นใจในคุณภาพค่อยขยายไปยังจุดอื่น และขยับขึ้นเป็น `clef` เมื่องานนั้นต้องการความแม่นสูงขึ้น
