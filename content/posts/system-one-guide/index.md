ช่วงกลางเดือนกันยายนถึงตุลาคม 2026 มี decision model เปิดตัวสี่เจ้าในรอบเดือนเดียว บทความนี้รวมภาพรวมของสาย System One ทั้งหมดไว้ในที่เดียว ตั้งแต่วิธีทำงานที่เหมือนกันทุกเจ้า ราคา จุดเด่นของแต่ละตัว ไปจนถึงหลักการเลือกใช้ให้เหมาะกับงาน

## System One คืออะไร ทำไมถึงมาตอนนี้

ชื่อ System One มาจากหนังสือ Thinking, Fast and Slow ของ Daniel Kahneman ที่แบ่งการคิดของคนเป็นสองระบบ System 1 คือระบบคิดเร็วที่ตัดสินใจจากสัญชาตญาณและรูปแบบที่จำได้ ใช้ข้อมูลไม่มากและจบได้ในเสี้ยววินาที ส่วน System 2 คือระบบคิดช้าที่ใช้เวลาใคร่ครวญยาว TypeSafe เป็นผู้ตั้งชื่อตระกูล API สายใหม่นี้ด้วยชื่อแรกของ Kahneman เพื่อสื่อว่าโมเดลกลุ่มนี้ทำงานแบบคิดเร็ว รับข้อมูลปุ๊บแล้วสรุปผลปั๊บ

งานอย่างเช่นข่าวนี้ควรถือว่าเกี่ยวข้องไหม ตั๋วนี้ควรส่งให้ทีมไหน คำตอบถูกจัดไว้เป็นชุดอยู่แล้ว LLM ทั่วไปที่รับงานนี้จะสร้างข้อความตอบกลับมาให้เรา parse อีกชั้น บางรอบตอบนอกแบบฟอร์ม บางรอบตีความพลาด ทั้งที่ปลายทางต้องการแค่ตัวเลขไปเทียบเกณฑ์

สาเหตุที่เรื่องนี้เป็นกระแสช่วงนี้เพราะผู้เล่นใหญ่เปิดตัวไล่กัน Jev จาก TypeSafe วันที่ 15 ก.ย.2026 ตามด้วย Decisions API จาก OpenAI ที่ประกาศวันที่ 29 ก.ย.2026 งาน DevDay ในรูปแบบ limited preview ก่อนเข้า public beta และ GA วันที่ 22 ต.ค.2026 ต่อด้วย Clef ของ Cloudflare วันที่ 1 ต.ค.2026 และ Laya จาก Convai Innovations ที่ประกาศช่วงเดียวกัน เวลาไม่ถึงหกสัปดาห์มี decision model ให้เลือกใช้สี่เจ้า

อีกเหตุผลหนึ่งอธิบายได้ด้วยชื่อของ Jev ที่ TypeSafe ตั้งตาม William Stanley Jevons พร้อมแนวคิดว่าทุกครั้งที่ต้นทุนของปัญญาลดลงได้หลายเท่าตัว งานที่เคยเป็นไปไม่ได้จะเปิดออกเป็นชั้น ๆ ราคา input ระดับสิบเซนต์ต่อล้าน tokens ที่เห็นกันในตลาดตอนนี้ จึงเป็นส่วนที่ทำให้หลายทีมย้ายงานจำพวกการจำแนกและการจัดลำดับออกจาก LLM ตัวใหญ่

อีกสาเหตุหนึ่งคือการแบ่งงานในระบบปัจจุบันที่คนเริ่มวาง decision model ไว้บนเส้นทางรับคำขอ เพื่อตัดสินใจขั้นแรกว่าควรดำเนินการต่ออย่างไร แล้วส่งงานที่ต้องสร้างคำตอบหรือลงมือทำจริงต่อให้ LLM เป็นผู้รับช่วง Cloudflare เองก็วาง Clef ไว้ในแนวทางนี้ คือให้โมเดลตัดสินใจนำหน้าแล้วค่อยตามด้วยโมเดลสร้างภาษา

คนในสายเรียกงานแบบนี้ว่า smart if-statement คือจุดที่เงื่อนไขในโค้ดเขียนแบบตายตัวไม่ได้ เช่น ข้อความนี้เร่งด่วนไหม ภาพนี้มีรหัสผ่านไหม ระบบเดิมที่แก้ปัญหานี้คือส่งไปให้ LLM แล้ว parse คำตอบที่ได้กลับมา แต่ decision model ตอบด้วย probability แทน โค้ดโดยรอบจึงจำกัดอิสระของโมเดลได้ และประกอบเข้ากับระบบเดิมได้ง่ายกว่า

## หลักการทำงานที่เหมือนกันทุกเจ้า

ทุกเจ้ารับของเดียวกันในการเรียกแต่ละครั้ง คือ state หรือข้อมูลที่จะใช้ตัดสินใจ กับ questions ที่ระบุชนิดคำตอบไว้ชัด มีสามชนิดที่ใช้กันหมด คือ `noul` สำหรับคำถามใช่หรือไม่ `choice` สำหรับเลือกจากชุดตัวเลือก และ `score` สำหรับให้คะแนนตามระดับที่เรียงไว้ ผลที่ได้กลับมาคือ probability ของทุกตัวเลือกในรอบเดียว

เพราะโมเดลไม่ได้สร้างข้อความใด ๆ ตอบกลับ คำตอบที่อยู่นอกชุดตัวเลือกจึงเป็นไปไม่ได้ และฝั่งรับผลไม่มี JSON เสีย ๆ หาย ๆ ให้ต้องซ่อม โค้ดที่รับ probability ทำงานง่ายคืออ่านค่าแล้วเทียบกับ threshold ที่เขียนไว้ ค่าสูงกว่าเกณฑ์ก็ผ่านอัตโนมัติ ค่ากลางก็ส่งให้คนตรวจต่อ ข้อกำหนดของแต่ละเจ้าที่ควรรู้คือต่อหนึ่งคำขอถามได้สูงสุด 64 คำถาม ตัวเลือกของ `choice` รับตั้งแต่ 2 ถึง 255 ข้อ และ `score` รับตั้งแต่ 2 ถึง 10 ระดับ

ด้านวิธีฝึก TypeSafe ตั้งชื่อเทคนิคของตัวเองว่า RLCD ย่อมาจาก Reinforcement Learning for Calibrated Decisions โดยฝึกให้โมเดลคืน probability ที่เทียบเกณฑ์ได้จริง Cloudflare ใช้ชื่อ RLCD เรียกขั้น reinforcement learning ของ Clef เช่นกัน สองเจ้านี้จึงมีรากวิธีฝึกที่ใกล้เคียงกัน

![แผนภาพ หนึ่งคำขอ: state และ questions เข้า decision model แล้วได้ probability กลับในคำขอเดียว](images/guide-diagram.png)

รูปแบบการเรียกจะหน้าตาประมาณนี้ (ตัดให้สั้น เฉพาะส่วนสำคัญ)

```json
{
  "state": "ลูกค้ารายงานว่าปุ่ม export ค้างใน Safari แต่ Chrome ใช้ได้ปกติ",
  "questions": {
    "category": { "type": "choice", "instructions": "ticket นี้เป็นประเภทไหน",
      "criteria": { "bug": "มีอะไรพังหรือทำงานผิด", "feature": "ขอของที่ยังไม่มี", "billing": "ค่าใช้จ่ายและใบแจ้ง" } },
    "severity": { "type": "score", "instructions": "รุนแรงแค่ไหน",
      "criteria": ["เล็กน้อยไม่กระทบ", "ฟีเจอร์เสียแต่มีวิธีใช้แทน", "ปิดงานได้ทั้งระบบ"] },
    "has_repro": { "type": "noul", "instructions": "มีขั้นตอน reproduce ไหม" }
  }
}
```

และคำตอบที่กลับมาเป็นแบบนี้ ไม่มีข้อความอื่นใดปน

```json
{
  "answers": {
    "category": { "choice": "bug", "probabilities": { "bug": 0.93, "feature": 0.04, "billing": 0.01, "other": 0.02 } },
    "severity": { "score": 1, "probabilities": [0.08, 0.71, 0.21] },
    "has_repro": { "noul": 0.15 }
  },
  "usage": { "input_tokens": 214, "output_tokens": 0 }
}
```

ค่าเหล่านี้พร้อมเทียบเกณฑ์ในโค้ดได้ทันที เช่น `category.bug > 0.8` ก็โยนเข้าสายแก้ไข `has_repro` ต่ำกว่า 0.3 ก็เติมคำถามให้ผู้แจ้งก่อนปิดงาน

ตัวอย่างการเรียกจริงใน pipeline ของผมคือส่งสถานะของข่าวหนึ่งเข้าไปพร้อมคำถาม `choice` สี่ข้อว่าข่าวนี้เกี่ยวข้องไหม ควรจัดอันดับแค่ไหน แนวโน้มเป็นบวกหรือลบ และผ่าน publish gate หรือไม่ ทุกคำถามได้ probability กลับมาในคำขอเดียว โค้ดฝั่งรับจึงตัดสินใจต่อได้ทันที ไม่ต้องวนเรียกหลายรอบเพื่อแยกคำตอบทีละข้อ
## ผู้เล่นทั้งสี่: Jev, Clef, OpenAI Decisions API, Laya

ทั้งสี่เจ้าทำงานบนหลักการเดียวกันที่อธิบายไว้ข้างต้น ต่างกันตรงที่ใครเป็นเจ้าของ ราคาเท่าไหร่ รันที่ไหนได้บ้าง และเก่งงานแบบไหน

| เจ้า | เจ้าของ | เปิดตัว | เปิด weights | input ต่อ 1M |
| --- | --- | --- | --- | --- |
| Jev | TypeSafe | 15 ก.ย.2026 | ไม่ | $0.042 |
| Clef | Cloudflare | 1 ต.ค.2026 | ใช่ | $0.24 / $0.038 |
| Decisions API | OpenAI | 29 ก.ย.2026 | ไม่ | $0.10 |
| Laya | Convai Innovations | ก.ย.2026 | ใช่ | ฟรี self-host |

### Jev (TypeSafe)

Jev เป็นเจ้าแรกของรอบนี้ เปิดตัววันที่ 15 ก.ย.2026 ให้บริการผ่าน API อย่างเดียวและปิดน้ำหนักโมเดล (closed) ราคาอยู่ที่ $0.042 ต่อ 1M input tokens โดย output ฟรี ตัวเลข latency ที่ vendor ให้มาอยู่ที่ 70 ถึง 500 มิลลิวินาทีต่อคำขอ ส่วน benchmark อิสระอย่าง AbdelStark และ nibzard วัดได้ p50 ที่ 236 ถึง 276 มิลลิวินาที ตอนนี้ยังเป็นรูปแบบ early access หรือ waitlist โดยมีรายงานว่าการรับสมัครใหม่หยุดไปตั้งแต่วันที่ 22 ก.ย.

ชื่อเสียงด้านความแม่นมาจาก benchmark อิสระที่วัดได้ typed-decisions ที่ 0.727 และ Banking77 ที่ 0.870 ส่วนค่า calibration หรือ ECE อยู่ที่ 0.246 และงานประเมิน agent อย่าง Respan ได้ 0.932 เทียบกับ Laya base ที่ 0.542
### Clef (Cloudflare)

Clef ตามมาวันที่ 1 ต.ค.2026 และแบ่งเป็นสามรุ่น `clef` ตัวหลัก 27B ที่ $0.24 ต่อ 1M input tokens โดยมี context 65,536 และรับรูปได้ 4 รูปต่อคำขอ, `clef-flash` ขนาด 9B ที่ $0.038 ซึ่งลดลงมาจาก $0.09 เมื่อวันที่ 9 ต.ค.2026 และมี hosted context 24,576, ส่วน `clef-omni` สำหรับงานเสียงและวิดีโอที่ $0.15 กับ context 64K ทุกรุ่นไม่คิดค่า output

ความเร็วที่ changelog วันที่ 1 ต.ค.2026 รายงานคือ median 209.3 มิลลิวินาทีสำหรับ `clef` และ 38.8 มิลลิวินาทีสำหรับ `clef-flash` โดย Jev ในชุดทดสอบเดียวกันอยู่ที่ 524.1 มิลลิวินาทีจากการทดสอบ 43 รอบ จุดขายอีกข้อคือเปิดน้ำหนักภายใต้ Apache 2.0 ดาวน์โหลดจาก Hugging Face ไปรันเองได้ ทั้งยังใช้ API แบบ System One ของ TypeSafe โค้ดที่เขียนรอ Jev ไว้จึงสลับมาเรียก Clef ได้ด้วยการเปลี่ยนชื่อโมเดล

ด้านผลทดสอบ Cloudflare รายงาน BFCL แบบ case-exact ที่ 98.47 ถึง 98.76 สำหรับ flash, BANKING77 macro-F1 ที่ 94.20 และ CLINC150 รวม OOS ที่ 97.43 พร้อมระบุว่าโมเดลตระกูลนี้ทำคะแนนสูงสุด 7 ใน 10 benchmark บน Jev Decision Index และมีบริการ fine-tune ด้วย RL สำหรับ design partner รวมถึงนโยบาย zero data retention ใครอยากอ่านรายละเอียดการใช้งานและตารางราคาฉบับเต็ม อ่านรีวิวฉบับเต็มที่ [รีวิว Clef](/posts/clef-review/)
### OpenAI Decisions API

OpenAI ประกาศ Decisions API บนงาน DevDay วันที่ 29 ก.ย.2026 ในรูปแบบ limited preview ต่อมาเข้า public beta และ GA วันที่ 22 ต.ค.2026 โดยรันอยู่บน GPT-6 Luna การคิดราคาตามประกาศคือจ่ายเฉพาะ input ในอัตรา $0.10 ต่อ 1M tokens โดยไม่มีค่า output ซึ่งแหล่งข้อมูลบางแห่งยังสับสนกันเรื่องค่า cache อยู่ จึงควรยึดตัวเลขนี้ตามประกาศ

API นี้รับทั้งข้อความและรูปภาพ แล้วคืนคำตอบแบบใดแบบหนึ่งจากสามแบบคือ probability, selection และ rubric score ฝั่ง OpenAI ระบุว่าเร็วกว่าการเรียก GPT-6 Luna ผ่าน Responses API ได้ถึง 10 เท่า ช่วง preview ยังไม่มีเอกสาร API เต็มรูปแบบ หลายแหล่งยังหาหน้า docs ไม่เจอ ใครที่จะนำไปใช้จริงจึงต้องตามอัปเดตจากหน้าเอกสารกันต่อ

### Laya (Convai Innovations)

Laya ต่างจากสามเจ้าข้างบนตรงที่เปิดน้ำหนักภายใต้ Apache 2.0 ตัวโมเดลเล็กเพียง 421M พารามิเตอร์ สร้างจาก ModernBERT-large ต่อเข้ากับ typed decision head ติดตั้งด้วย `pip install laya` และรันในเบราว์เซอร์ได้ ความเร็วที่วัดบน Tesla T4 อยู่ที่ 32.8 ถึง 39.5 มิลลิวินาทีต่อคำถาม และเมื่อ batch 10 คำถามพร้อมกันอยู่ที่ราว 72 มิลลิวินาที

จุดที่ต้องระวังคือ Laya ไม่เหมาะกับการใช้งานแบบ zero-shot checkpoint พื้นฐานทำได้ 0.362 บนชุด typed-decisions ขณะที่การสุ่มเดาได้ 0.318 และการเดาค่ามากสุดได้ 0.461 ต้อง fine-tune ก่อนใช้งานจริง โดย checkpoint ที่ฝึกด้วย 1,200 เคสทำได้ 0.766 เทียบกับ Jev ที่ 0.727

เมื่อเทียบกันเป็นชุดข้อมูล Jev ยังนำในหลายรายการ เช่น Banking77 ที่ 0.870 เทียบกับ 0.425 และ Respan ที่ 0.932 เทียบกับ 0.542 แต่ด้าน calibration Laya ทำได้ดีกว่าด้วย ECE 0.081 เทียบกับ Jev ที่ 0.246 หลัง temperature fitting และมีข้อจำกัดเรื่องตัวเลือกเกิน 20 ข้อความที่ความแม่นลดลง เพราะ head มี budget แค่ 256 token รวมถึง ordinal scoring ที่เป็นจุดอ่อนที่สุด
## ใช้อะไรได้บ้าง

งานที่เหมาะกับ decision model คืองานที่คำตอบถูกจัดไว้เป็นชุดอยู่แล้ว ไล่ตั้งแต่

- classify ข้อความเข้าหมวด เช่น อ่าน intent ของผู้ใช้แล้วส่งต่อให้ flow ที่ถูกต้อง หรือจัดข่าวเข้าสายก่อนเข้า pipeline
- triage ตั๋วและงานแจ้งปัญหา ว่าเร่งด่วนแค่ไหนและทีมไหนควรรับ โดยไม่ต้องให้คนนั่งดูทีละใบ
- เลือก tool ให้ agent ว่าคำสั่งชุดนี้ควรเรียก function ตัวไหน ซึ่ง probability ที่ได้ใช้เทียบเกณฑ์ความมั่นใจในโค้ดต่อได้ทันที
- gate และ guardrail ตรวจว่าเนื้อหาหรือพฤติกรรมเข้าเกณฑ์ต้องบล็อกหรือไม่
- ให้คะแนนตาม rubric แทน LLM judge ที่ต้องอ่านคำตอบแล้วเขียนคะแนนกลับมา เพราะค่าตัวเลขคงที่และเทียบผลข้ามรอบได้
- จัดลำดับและตัดสินใจผ่านไม่ผ่านตามจุดต่าง ๆ ของ pipeline เช่น relevance, sentiment และ publish gate
- ดึงข้อมูลจากข้อความหรือเอกสาร เช่น อ่านค่าจากฟอร์มหรืออีเมลแล้วส่งเข้า field ของระบบต่อ
- ประมวลผลข้อมูลปริมาณมากแบบ map-reduce แปลงข้อมูลชุดใหญ่ให้เป็นค่าที่ใช้ตัดสินใจต่อได้โดยไม่ต้องสร้างรายงานยาว ๆ
- งาน real-time ที่เวลาตอบสนองมีผลต่อประสบการณ์ผู้ใช้ เช่น ตัดสินใจภายในหนึ่งร้อยมิลลิวินาทีระหว่างรอหน้าจอโหลด

ตัวอย่างโครงคำถามที่เขียนได้จากงานจริงคือ support ticket หนึ่งฉบับ ส่งเข้าไปพร้อมคำถามสามข้อ คือ `choice` ว่าเป็น bug, feature request, ค่าใช้จ่าย หรืออื่น ๆ, `score` ว่ารุนแรงระดับไหนตั้งแต่ไม่กระทบจนถึงปิดการใช้งานได้ และ `noul` ว่ามีขั้นตอน reproduce ระบุไว้ไหม ทั้งสามคำตอบกลับมาในคำขอเดียวพร้อม probability โค้ดจึงเลือกสายงาน เรียงลำดับความรุนแรง และส่งต่อให้ทีมรับผิดชอบได้ทันทีโดยไม่ต้องรอคนอ่านตั๋วทีละใบ

case study จริงของผมคือ pipeline triage ข่าวของเว็บตัวเอง ที่รันสองรอบต่อวันคือ morning-brief และ evening-brief แต่ละรอบมี decision stage หลายตัวทำงานร่วมกัน ได้แก่ relevance ว่าข่าวนี้เกี่ยวกับโจทย์ไหม rank ว่าควรจัดลำดับความสำคัญแค่ไหน sentiment ว่าเป็นบวกหรือลบ และ gate สุดท้ายที่ตัดสินใจว่าผ่านเกณฑ์จะนำไปเผยแพร่หรือไม่ เดิมผมใช้ iApp OpenThai SystemOne ซึ่งช่วง preview ให้ใช้ฟรี 1,000 decisions ต่อวันต่อ key พอดีกับงานสองรอบ
## ดีอย่างไร: ข้อได้เปรียบเทียบกับ LLM

เรื่องแรกคือความเร็ว LLM ทั่วไปใช้เวลา end-to-end ตั้งแต่ 3 ถึง 329 วินาทีตามตัวเลขของ TypeSafe ส่วน decision model อยู่ที่ Jev 70 ถึง 500 มิลลิวินาที หรือ p50 ที่ 236 ถึง 276 มิลลิวินาทีจาก benchmark อิสระ clef-flash ที่ median 38.8 มิลลิวินาที และ OpenAI ระบุว่า Decisions API เร็วกว่าการเรียก GPT-6 Luna ผ่าน Responses API ได้ถึง 10 เท่า งานที่อยู่บนเส้นทางรับคำขอจึงใส่ decision model ได้โดยผู้ใช้ไม่รู้สึกว่าช้า

![กราฟแท่งเทียบเวลาตอบต่อคำขอ Laya 39.5, clef-flash 38.8, Clef 209.3 และ Jev 524.1 มิลลิวินาที](images/guide-latency.png)

| ตัวเลขความเร็ว | ค่าที่วัดได้ |
| --- | --- |
| Laya (Tesla T4, 1 คำถาม) | 32.8 ถึง 39.5 ms |
| clef-flash (median) | 38.8 ms |
| Clef (median) | 209.3 ms |
| Jev (p50, benchmark อิสระ) | 236 ถึง 276 ms |
| Jev (median ในชุดทดสอบของ Cloudflare) | 524.1 ms |
| LLM ทั่วไป (end-to-end) | 3 ถึง 329 วินาที |

เรื่องที่สองคือต้นทุน LLM ทั่วไปคิด input อยู่ที่ $0.20 ถึง $10 ต่อ 1M tokens และคิด output แพงกว่า input ราว 5 เท่า ขณะที่ decision model ในตลาดนี้คิดเฉพาะ input และไม่คิด output เลย เพราะโมเดลไม่ได้สร้างข้อความตอบกลับ งานที่ต้องเรียกหลายพันครั้งต่อวันจึงประหยัดกว่าชัดเจน

เรื่องที่สามคือรูปแบบคำตอบที่คงที่ ทุกคำขอได้ probability กลับมาในรูปเดียวกัน ไม่ต้องเขียนโค้ด parse ภาษา ไม่ต้องกันเคสที่โมเดลตอบนอกแบบ และไม่มี JSON เสีย ๆ ให้ซ่อม probability ทุกตัวเลือกยังเปิดทางให้ตั้งเกณฑ์แยกชั้นในโค้ดได้ เช่น ค่าสูงผ่านอัตโนมัติ ค่ากลางส่งให้คนตรวจ ซึ่งถ้าจะให้ LLM ทำเหมือนกันต้องพึ่ง prompt และการตีความคำตอบที่ไม่คงที่เท่ากันทุกรอบ

เรื่องที่สี่คือความมั่นใจที่มาพร้อมคำตอบ TypeSafe ระบุว่า LLM ทั่วไปถ้าถูกขอให้ประเมินความมั่นใจมักจะประเมินเกินไปและไม่สม่ำเสมอ ทั้งที่งานที่ automate ได้จริงต้องการตรงกันข้าม คือโมเดลบอกได้ว่าข้อนี้มั่นใจแค่ไหน แล้วค่ามั่นใจที่สูงควรสอดคล้องกับความแม่นที่สูงตามไปด้วย decision model ทุกคำขอจึงมาพร้อม probability และ confidence ช่วยให้ตั้งเกณฑ์แบ่งชั้นได้ชัดว่าข้อนี้ผ่านเอง ข้อนี้ส่งคนตรวจ หรือข้อนี้ส่งต่อให้โมเดลที่ใหญ่กว่าช่วยดูซ้ำ

เรื่องที่ห้าคือความคงเส้นคงวาในการตอบ ข้อมูลเดิมที่ใกล้เคียงกันมักได้คำตอบใกล้เคียงกันทุกรอบ และการกำหนดโครงสร้างคำตอบไว้ล่วงหน้าทำให้ไม่มีโอกาสเกิด type error ในทางทฤษฎี งานที่ต้องการผลซ้ำได้เหมือนกันทุกครั้งเวลาเทสต์หรือไล่ย้อนหลังจึงเหมาะกับโมเดลแนวนี้

โอกาสเสริมอีกอย่างคือความง่ายในการวัดผล เพราะทุกคำขอคืนค่าในรูปแบบเดิมเสมอ ระบบจึงเก็บ probability ไปทำรายงานเฉลี่ยรายวันหรือเทียบกับรอบก่อนได้ทันที จุดที่ค่าเริ่มเปลี่ยนจากเดิมจึงถูกเห็นในฐานะตัวเลขที่อ่านได้ ไม่ใช่สัญญาณคลุมเครือที่ต้องตีความเอง

## ตัวอย่างแบบก่อนและหลัง

สามกรณีนี้เทียบให้เห็นเป็นตัวเลขว่าหลังเปลี่ยนมาใช้ decision model แล้วได้อะไรกลับมาบ้าง

### กรณีที่ 1: จำแนกหมวดเว็บไซต์

ทีม Threat Intelligence ของ Cloudflare มี workflow เปิดและจำแนกหมวดโดเมนเว็บ ตอนใช้ LLM ทั่วไปอย่าง gpt-oss-120b ใช้เวลา 4.7 วินาทีและได้ผลลัพธ์แค่สองคลาส พอเปลี่ยนมาใช้ Clef คู่กับ Browser Run เวลาลดเหลือ 2.2 วินาที แล้วยังได้ probability ของทุกคลาส เช่น โอกาสเป็นเว็บแฟชั่น 95% e-commerce 85% และโอกาสเป็น phishing ต่ำกว่า 1% ทุกค่าเอาไปเทียบเกณฑ์ในระบบทันทีโดยไม่ต้องรอคนมานั่งอ่านผล

### กรณีที่ 2: pipeline ข่าวของผมที่เคยดับ

ช่วงที่ decision engine เดิมค้าง HTTP 500 ตั้งแต่วันที่ 13 พ.ย.2026 ผมไม่ได้ตัวเลขของ stage ไหนออกมาเลยทั้งที่ pipeline ยังรันอยู่ พอวันที่ 18 พ.ย.2026 สลับไปใช้ Clef บน Workers AI ทั้งสอง profile ตัวเลขของทุก stage กลับมาทันที relevance ผ่าน 14 จาก 17 รายการ และ gate ได้ 0.02 กับ 0.74 โดยมี cron เช็คซ้ำวันที่ 19 พ.ย.เวลา 07:30 ยืนยันว่าค่าออกมาทุกเช้า ตอนนี้ผมอ่าน probability ของแต่ละ stage ออกจาก log ได้ทุกวันแทนการเดาระบบจากความเงียบช่วงล่ม

### กรณีที่ 3: ต้นทุนต่อหนึ่งล้านคำขอ

ถ้ามีคำขอ 1 ล้านครั้ง ครั้งละ 500 tokens การเรียก `clef-flash` ตกที่ $19 และ median latency 38.8 มิลลิวินาทีทำให้ตัวตัดสินใจตัวนี้วางบน hot path ได้จริง ตัวเลขชุดนี้ยังเป็นจุดเริ่มของคำถามเรื่องงบที่ต่อไปในหัวข้อค่าใช้จ่ายจะเทียบทั้งสี่เจ้าให้ดูพร้อมกัน
## ค่าใช้จ่ายเทียบกัน

ราคาของ decision model ง่ายกว่า LLM ตรงที่คิดเฉพาะ input เท่านั้น ตารางนี้รวมทุกเจ้า ณ วันที่ที่แต่ละเจ้าประกาศไว้

| เจ้า | input ต่อ 1M | output | เปิด weights |
| --- | --- | --- | --- |
| Jev | $0.042 | ฟรี | ไม่ |
| Clef | $0.24 (27B) / $0.038 (9B flash) | ฟรี | ใช่ (Apache 2.0) |
| OpenAI Decisions | $0.10 | ฟรี (ตามประกาศ) | ไม่ |
| Laya | ฟรี self-host (บวกค่า GPU) | ฟรี | ใช่ (Apache 2.0) |

ลองประเมินเป็นตัวเงินง่าย ๆ ด้วยสมมติฐาน 1 ล้านคำขอ ครั้งละ 500 tokens ซึ่งเท่ากับ 500 หน่วยของราคาต่อ 1M จะได้ Jev ที่ $21, `clef-flash` ที่ $19, `clef` ตัวหลักที่ $120 และ OpenAI ที่ $50 จากอัตรา input $0.10 ต่อ 1M ตัวเลขของ Jev ตรงกับที่ eesel.ai เทียบไว้ ส่วน LLM อย่าง GPT-6 Luna ในการคำนวณชุดเดียวกันได้ $27.50 แบบ batch และ $55 แบบ standard

Laya เป็นเจ้าเดียวที่ไม่มีค่า license เพราะรันเองได้ ต้นทุนจริงของ Laya ยังมีทั้งค่า GPU เวลาติดตั้ง และเวลา fine-tune ที่ต้องทำก่อนใช้งาน ข้อควรทำเสมอก่อนวางแผนงบคือการเช็ค changelog และหน้าราคาของแต่ละเจ้า เพราะตัวเลขเหล่านี้เป็นราคา ณ วันที่ที่ระบุและเปลี่ยนได้ตลอด

วิธีประเมินค่าใช้จ่ายของงานตัวเองก็ทำง่าย เริ่มจากนับจำนวนคำขอต่อวัน คูณด้วย tokens ต่อคำขอ คูณจำนวนวันในเดือน แล้วหารด้วยหนึ่งล้านเพื่อแปลงเป็นหน่วยราคา ตามด้วยคูณอัตราของเจ้าที่เลือก แค่นี้ก็ได้ตัวเลขงบรายเดือนคร่าว ๆ ก่อนตัดสินใจผูกระบบจริง
## หลักการเลือกใช้

ถ้าจะเลือกสักเจ้าให้เริ่มจากเงื่อนไขของงานตัวเองแล้วไล่ดูตามนี้

- ต้องการรันเองหรือข้อมูลห้ามออกนอกระบบ เลือก Clef หรือ Laya ซึ่งเปิด weights ภายใต้ Apache 2.0 โดย Laya เล็กและเร็วกว่า แต่ต้อง fine-tune ก่อน ส่วน Clef ตัวใหญ่กว่าและหยิบมาใช้ได้เลย
- ต้องการความเร็วสูงสุดบนคลาวด์ `clef-flash` ที่ median 38.8 มิลลิวินาที
- ต้องการราคาถูกสุดแบบ hosted Jev ที่ $0.042 ต่อ 1M input tokens
- อยู่ในจักรวาล OpenAI อยู่แล้ว หรือต้องการส่งข้อความและรูปเข้าที่เดียว Decisions API คือคำตอบที่เข้าทางที่สุด
- ต้องการให้ confidence ที่คืนมาเชื่อถือได้ ให้ดูค่า ECE เป็นหลัก เช่น Laya ที่ 0.081 หลัง temperature fitting เทียบกับ Jev ที่ 0.246
- งาน classification ที่มีตัวเลือกเยอะระดับสิบ ๆ หมวด Jev ทำ Banking77 ได้ 0.870 และ Clef รายงาน macro-F1 ที่ 94.20 ส่วน Laya base ได้ 0.425 จึงไม่ใช่ตัวเลือกแรกสำหรับงานแบบนี้

ผู้เล่นอื่นที่ควรรู้เพิ่มอีกหน่อย Kev จาก Jared Palmer เป็น open weights ขนาด 9B ที่อยู่บน Hugging Face Decision3.0 เป็นโมเดล open งาน multimodal ตั้งแต่ 0.6B ถึง 27B และมีรายงานในชุมชนว่าขึ้นอันดับหนึ่งบนบอร์ด Jev Decision Index ส่วน Gemini Decision กับ Microsoft Decision 1 มีให้เห็นในการเปรียบเทียบของ Opper ตลาดนี้ขยับเร็ว จึงเช็ค benchmark ล่าสุดเสมอ

การเริ่มทดสอบของผมมาจากที่ flaviocopes แนะนำ คือเขียน inputs 20 ชิ้นที่รู้คำตอบอยู่แล้วจากงานจริง แล้วยิงเข้าทุกเจ้าเพื่อเทียบ accuracy และ confidence ที่คืนมา วิธีนี้ใช้เวลาไม่นานและช่วยตัดเจ้าที่ไม่เข้ากับงานได้ก่อนจะผูกระบบจริงเข้ากับ API ของเจ้าไหน

ถ้าจะให้เป็นขั้นตอน ก็คือเริ่มจากถามตัวเองว่างานนี้นิยามคำตอบที่ถูกต้องได้จริงไหม ถ้ายังนิยามไม่ได้ให้ไปออกแบบ taxonomy ของคำตอบก่อน ได้แล้วค่อยดูเงื่อนไขบังคับ เช่น ข้อมูลห้ามออกนอกระบบ หรือเวลาตอบสนองต้องต่ำกว่ากี่มิลลิวินาที จากนั้นคัดให้เหลือสองเจ้าแล้วยิงชุดทดสอบ 20 inputs เทียบกัน จึงค่อยตัดสินใจผูกระบบจริงเข้ากับเจ้าที่ชนะ
## ข้อจำกัดที่ควรรู้ก่อนเริ่ม

ข้อแรก decision model ตอบได้เฉพาะตัวเลือกที่เราออกแบบไว้เท่านั้น งานที่ต้องร่างข้อความยาว แต่งประโยค หรือให้เหตุผลอิสระ จึงยังเป็นหน้าที่ของ LLM ที่ต้องรับช่วงต่อ

ข้อสอง คุณภาพของคำตอบผูกกับการออกแบบคำถามโดยตรง ถ้าชุด `choice` ไม่ครอบคลุมสถานการณ์จริง probability ที่ได้ก็สะท้อนชุดตัวเลือกแคบ ๆ นั้น งานที่ยังตอบไม่ได้ว่าคำตอบที่ถูกต้องคืออะไร จึงยังไม่ถึงจังหวะที่ต้องย้ายมาใช้ decision model ระหว่างนั้นลองให้ LLM ช่วยร่าง taxonomy ของคำตอบก่อน แล้วค่อยย้ายเมื่อเกณฑ์นิ่ง

ข้อสาม ข้อจำกัดเชิงตัวเลขของแต่ละเจ้า Jev และ Clef ถามได้สูงสุด 64 คำถามต่อหนึ่งคำขอ ถ้ามีหัวข้อตัดสินใจเกินกว่านั้นต้องแบ่งส่งหลายรอบและกระทบวิธีเขียนโค้ดฝั่งเรียกใช้ Laya มีข้อจำกัดเพิ่มตรงที่ตัวเลือกเกิน 20 ข้อแล้วความแม่นลดลง เพราะ head budget แค่ 256 token และ ordinal scoring ก็เป็นจุดอ่อนที่สุด ไหนจะ Laya base ที่ทำได้แค่ 0.362 ตอนยังไม่ fine-tune

ข้อสี่ ความเสี่ยงเรื่องการพึ่งพา service ราคาและเงื่อนไขของ hosted เปลี่ยนได้เสมอ บทเรียนของผมคือ API เจ้าอื่นค้าง HTTP 500 ต่อเนื่องหลายวันโดยไม่มีประกาศ ระบบจึงควรมี fail-over และจุด fail-open ที่ออกแบบไว้ล่วงหน้า ส่วนคนที่จะ self-host ต้องเช็คฮาร์ดแวร์ก่อน เครื่องผมเป็น Xeon รุ่น Ivy Bridge ไม่มีชุดคำสั่ง AVX2 ทำให้ torch เวอร์ชันใหม่กว่า 2.4 crash ด้วย invalid opcode ตอนโหลดโมเดล

ข้อห้า benchmark ในตลาดนี้ถูกแทนที่เร็ว คะแนนที่เห็นวันนี้อาจถูกแซงในสัปดาห์หน้า จึงควรเช็คคะแนนล่าสุดก่อนตัดสินใจผูกกับเจ้าไหน และดูค่า calibration อย่าง ECE ประกอบด้วย เพราะ accuracy สูงอย่างเดียวไม่บอกว่า probability ที่คืนมาเชื่อถือได้แค่ไหนในทางปฏิบัติ

ข้อหก คำตอบไม่มีคำอธิบายมาด้วย decision model คืน probability อย่างเดียว ไม่ได้บอกเหตุผลว่าทำไมถึงให้ค่านั้น งานที่ผู้ตรวจต้องรู้ว่าโมเดลประเมินอย่างไร เช่น รายงานตรวจสอบหรือคำตัดสินที่มีคนโต้แย้ง จึงต้องเก็บเหตุผลเพิ่มจากแหล่งอื่น เช่น ส่งข้อมูลชุดเดียวกันไปให้ LLM แต่งคำอธิบายแยก หรือให้คนตรวจสรุปเหตุผลเอง

## สรุป

ภาพรวมของทั้งสี่เจ้าพอสรุปสั้น ๆ ได้แบบนี้ Jev เป็น hosted ที่ราคาถูกที่สุดที่ $0.042 ต่อ 1M input tokens Clef เป็นตัวที่ได้ความเร็ว ราคา และ open weights ไปพร้อมกัน โดย `clef-flash` ที่ median 38.8 มิลลิวินาทีเหมาะกับงานบน hot path OpenAI Decisions API เหมาะกับคนที่อยู่ใน ecosystem ของ OpenAI อยู่แล้วหรือต้องการส่งข้อความและรูปเข้าที่เดียว ส่วน Laya คือทางเลือก self-host ที่เล็กและเร็วเมื่อผ่านการ fine-tune แล้ว ข้อแลกเปลี่ยนคือการคุมข้อมูลทุกอย่างเอง

อีกสัญญาณที่ควรจับตาคือ API ของแต่ละเจ้าที่เริ่มใกล้เคียงกัน อย่าง Clef ใช้รูปแบบเดียวกับ System One ของ TypeSafe ทำให้โค้ดที่เขียนไว้กลางระหว่างเจ้าหนึ่งย้ายไปอีกเจ้าได้ด้วยการเปลี่ยนชื่อโมเดล ตลาดที่ย้ายง่ายแบบนี้ผู้ใช้ได้เปรียบ เพราะไม่ต้องผูกตายกับเจ้าเดียวเวลาถูกปรับราคาหรือหยุดให้บริการ

ใครที่สนใจ Clef เป็นพิเศษ ไม่ว่าจะเรื่องราคา การรับรูป หรือประสบการณ์ย้ายระบบจริงของผม ผมเล่าไว้เต็มใน [รีวิว Clef](/posts/clef-review/)

ถ้ายังไม่รู้จะเริ่มตรงไหน ให้กลับไปใช้วิธีทดสอบ 20 inputs ในหัวข้อหลักการเลือกใช้ แล้วย้ายทีละจุดโดยรันระบบเดิมคู่กันไปก่อน จนค่า probability ของทุก stage สอดคล้องกันหลายวันจึงค่อยปิดของเดิม
